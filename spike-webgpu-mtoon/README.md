# spike-webgpu-mtoon

*2026-11-19. AB-T-0553, WebGPU research 1 for M4 (AB-D-0261). Does `@pixiv/three-vrm` 3.5.5's MToon node material run on three r187 under `WebGPURenderer`, and if not, what is the smallest fix? Machine: M5 Max, macOS 27.3 (26C5047e). Chromium is Chrome for Testing 156 (headless, Metal). The WKWebView is the sandboxed `spike-physics/mac` wrapper.*

## Verdict

**Carry a six-line local patch to three-vrm 3.5.5's `lib/nodes/index.module.js`, and stay on three r187. With it, opaque MToon on `WebGPURenderer` matches the WebGL MToon we ship today.** That holds in Chromium and in WKWebView, on both origins, for Mira, Hana, a VRoid model, controlled feature scenes and a licence-filtered sample of 29 VRoid Hub characters. **Translucent materials will look different under WebGPU whatever we patch:** WebGPURenderer composites them in linear light, where WebGL composites them in sRGB. That's three's design, not MToon, and it's a look decision for M4 (below).

- **How it fails.** three r187 removed `transformedNormalView` from `three/tsl` ([mrdoob/three.js#34517](https://github.com/mrdoob/three.js/pull/34517)). It had been renamed `normalView` in r178 ([#31271](https://github.com/mrdoob/three.js/pull/31271)) and kept as a deprecated alias through r186. three-vrm 3.5.5 still imports the old name twice, in the lighting model's N·L and in the parametric rim's N·V. So the module can't even link:
  - **Node / browser:** `SyntaxError: The requested module 'three/tsl' does not provide an export named 'transformedNormalView'`
  - **Vite 8 (Rolldown):** both the dev pre-bundler and `vite build` fail hard with `[MISSING_EXPORT] "transformedNormalView" is not exported by three.tsl.js` (`results/vite-build-stock.txt`). An app that merely contains the import can't be built.
  - **webpack 5:** errors with no bundle (measured upstream in the #1890 thread).
- **Upstream.** The issue is open: [pixiv/three-vrm#1889](https://github.com/pixiv/three-vrm/issues/1889). The fix, [pixiv/three-vrm#1890](https://github.com/pixiv/three-vrm/pull/1890) (opened 2026-10-30), is open and not merged. Its thread includes a test report from this account and a maintainer leaning towards raising the floor to r178 alongside [#1878](https://github.com/pixiv/three-vrm/pull/1878) (bump to r186, also open). No release since 3.5.5 (2026-07-09). **No upstream version fixes it today.**
- **Fixing the load alone isn't enough.** With #1890's change only (`lib=loadonly`), MToon renders but doesn't match WebGL. With every MToon input on, 58–86% of character pixels differ by more than 8/255. This spike found four **fidelity bugs** in `MToonNodeMaterial`. None is r187-specific: stock 3.5.5 on r186 shows the same errors.
  1. **Matcap is mirrored left↔right.** `matcapUV.mul(1, -1).add(0, 1)` is meant as `uv · (1, −1) + (0, 1)`. But TSL's `mul`/`add` are variadic: `a.mul(1, −1)` is `a·1·(−1)`. So the result is `1 − uv` on both axes, which adds a U flip. The quadrant test proves it (`results/shots/*matcapTex_quad*`). three's own `MeshMatcapNodeMaterial` matches `MeshMatcapMaterial`, so the bug is in three-vrm.
  2. **The rim uses one view direction per mesh.** `mtoonParametricRim` takes `modelViewPosition`, which in TSL is the **object's origin** in view space (a per-object uniform), not the fragment's position. For a VRM, every rim pixel is computed against the direction to the model's feet. The fix is `positionView`, as the GLSL uses `vViewPosition`.
  3. **The rim lighting mix leaves out ambient light.** GLSL mixes the rim towards (direct + ambient irradiance)/π. The node model mixes towards 0 in `indirectSpecular`. The fix mixes towards `BRDF_Lambert(irradiance)` there. At ambient 0.6, leaving this out gives 8.8% of pixels off instead of 1.3%.
  4. **The UV-animation mask reads the wrong channel.** The node version reads R; the MToon spec and the GLSL read B. A sphere with a B-only mask doesn't animate on stock 3.5.5 and matches WebGL once patched (`model=spheres2`). The masks in the VRoid sample are greyscale, so this bug doesn't show there.
- **The fix:** [`patches/three-vrm-3.5.5-nodes-r187.patch`](patches/three-vrm-3.5.5-nodes-r187.patch), generated by `web/scripts/patch-three-vrm.mjs`. It changes six lines: the two #1890 import edits (r178+ branch) and the four fidelity fixes, one of which shares an import line. With it, controlled spheres go from PSNR 27.5 to 50.7 dB, and the matcap quadrant test reaches 79 dB. Mira, Hana and the VRoid model with every feature forced on reach SSIM ≥ 0.995 with ≤ 0.48% of character pixels off by more than 8/255. Run `patch-three-vrm.mjs --check` on every three-vrm bump: it fails loudly when the stock file changes.
- **Rejected: pinning three r186 with stock 3.5.5.** It loads, but it carries all three fidelity bugs (stock r186 vs WebGL: 67% of Mira's and 85% of the VRoid's character pixels off). r186's `WebGPURenderer` also drew the VRoid's cuffs, collar and skirt band in the wrong colour, with either library. WebGL is pixel-identical on r186 and r187. Pinning would also downgrade the whole engine from r187.
- **Translucency differs by design (decide in M4).** WebGL blends sRGB-encoded colour straight into the canvas. WebGPURenderer blends in linear light and encodes at output. three's own `MeshBasicMaterial` at opacity 0.5 measures 233,195,189 on WebGL against 233,198,195 on WebGPU, and those are the predicted sRGB-space and linear-space blends to the unit (`model=threealpha`). On the VRoid sample this is the whole of the three large outliers (UV-animated translucent overlays): hiding translucent materials takes them from 20–47% down to ≤ 1.3%. Linear is the physically correct blend, but sRGB-space blending is what VRMXG ships today, and this spike didn't establish which one VRoid authors tuned against. Options for M4: accept it; or have the render path blend in sRGB space (render to an 8-bit non-sRGB target with the encode in the material, as WebGL effectively does), which AB-T-0554 should cost along with the post stack.
- **Cost:** one vendored file (or patch-package entry) plus `--check`, until upstream releases #1890 and fixes for the four fidelity bugs. The fidelity bugs were filed upstream on 2026-11-19 with the operator's OK, each with a repro and a suggested fix: [#1904](https://github.com/pixiv/three-vrm/issues/1904) (matcap mirrored), [#1905](https://github.com/pixiv/three-vrm/issues/1905) (rim view direction), [#1906](https://github.com/pixiv/three-vrm/issues/1906) (rim lighting mix without ambient light) and [#1907](https://github.com/pixiv/three-vrm/issues/1907) (UV-animation mask channel). Drop each patch edit once a release fixes its issue; `--check` will flag the change.

## Results

The pass threshold is "looks the same". The numbers: SSIM on luma (11×11 Gaussian, σ 1.5) over the whole 512×768 frame, and **fg>8**, the share of character pixels whose largest channel differs by more than 8/255. WebGL `MToonMaterial` (GLSL) is the reference. `features=all` forces matcap, parametric rim (lighting mix 0.5), emissive and UV scroll and rotation on every MToon material, on top of the authored values (shade, toony, shift, normal maps, outlines). Spec's authored materials use no matcap, rim or UV animation, and its emissive map is black, so the spike clears that map. Raw data: `results/chromium.json`, `results/wkwebview.json`, `results/compare.json`.

**Controlled scene** (`model=spheres`: shade + world-space outline, rim, lit rim, matcap, emissive, UV-animated checker; flat colours, no loader), Chromium:

| | SSIM | fg>8 | max Δ | PSNR |
|---|---|---|---|---|
| stock 3.5.5 on r186 / #1890 only on r187 | 0.9883 | 32.5% | 104 | 27.5 dB |
| **patched, r187, WebGPU backend** | **0.9998** | **1.28%** | 40 | **50.7 dB** |
| patched, r187, WebGPURenderer on its WebGL2 backend | 0.9998 | 1.28% | 40 | 50.7 dB |

The second scene (`model=spheres2`: a B-only-mask UV sphere, three translucent spheres over an opaque one) gives 46.9% patched against 57.9% with #1890 only. The mask sphere matches once patched; all of the rest is the translucent spheres, which differ uniformly by the linear-vs-sRGB blend, as three's own `MeshBasicMaterial` does (`model=threealpha`: 22.7% of its pixels, max Δ 13; `results/shots/*threealpha*`, `*spheres2*`).

Shade, toony, outline, emissive and UV animation match even unpatched. The 1.28% left is a thin ring at the matcap disc's edge. three's `matcapUV` scales by 0.495 against MToon's 0.5, which three does on purpose to hide disc-edge artifacts. Cosmetic.

**VRoid Hub sample** (`results/vroid-sample.json`, `results/chromium-vroid.json`, `results/wkwebview-vroid.json`). The local crawl at `/Volumes/DEV_ARCHIVE/vroid-vrm-dataset` has 35,144 models. 11,991 pass a conservative licence filter: corporate commercial use allowed, use by others allowed, no R15, R18 or adult flag. Of those, 11,988 are VRM 0.x and 3 are VRM 1.0; 5 use UV animation and 7 a rim texture. `web/scripts/scan-vroid-dataset.py` picks a sample of 29: all 3 VRM 1.0, all 5 UV-animated, all 7 rim-textured, and 14 more 0.x exports spread over exporter versions (UniGLTF 1.24–2.64, the Blender add-on) and over rim and outline on and off. Pictures and models are never committed; the JSON keeps ids and the credit flag. Patched WebGPU vs WebGL, share of character pixels off by more than 8/255:

| case | Chromium median / ≤ 1% / worst | WKWebView median / ≤ 1% / worst | #1890 only, Chromium median / worst |
|---|---|---|---|
| body, authored | 0.10% / 24 of 29 / 47.1% | 0.49% / 19 of 29 / 45.8% | 0.82% / 48.5% |
| body, authored, translucent materials hidden | **0.01% / 26 of 29 / 3.5%** | **0.23% / 22 of 29 / 5.2%** | 0.71% / 46.3% |
| face, authored | 0.74% / 16 of 29 / 16.7% | 1.41% / 10 of 29 / 16.9% | 5.68% / 25.0% |
| body, every feature forced on | 0.46% / 22 of 29 / 21.3% | – | 72.1% / 87.1% |

- **The large outliers are translucency.** The three worst bodies (20–47%) are the UV-animated models whose animated layers are translucent. Hiding translucent materials takes each to ≤ 1.3%; zeroing emission barely changes them. It's the linear-light blending above.
- **What's left on opaque materials:**
  - One model (2000878…, an alpha-tested, double-sided material with a world-space outline and an outline-width texture) shows an outline crescent behind a sleeve on WebGPU only. Hiding outlines takes it to 0.00%. **Open:** a sixth difference, in the node outline for this combination, not chased.
  - The next worst (7741315…, 2.9%) is thin silhouette edges on an edge-heavy model, unchanged with outlines hidden. That's rasterisation, not shading.
- **VRM 1.0** (3 VRoid Studio exports) match at ≤ 0.07% (body) and ≤ 1.1% (face).
- **Caveat:** the fixed test pose raises the arms on VRM 0.x models (it doesn't account for 0.x's flipped rig). Both renderers get the same pose, so the comparison holds.

**Across runtimes:** WebGL frames are effectively identical between Chromium and WKWebView (max Δ ≤ 9, PSNR ≥ 69 dB; spheres bit-identical). WebGPU frames differ slightly between the two browsers (≤ 0.32% of character pixels, PSNR ≥ 47 dB; spheres bit-identical). That's the WebGPU implementations' rasterisation and precision, not MToon. Deterministic exports that must match across engines need this checked again in AB-T-0554.

**Load test in Node** (`results/repro-node.json`): r187 stock fails with the `SyntaxError` above. r187 patched, r186.1 stock and r186.1 patched all load and construct both an `MToonNodeMaterial` and an outline one.

## Warnings left (harmless)

- `THREE.TempNode: This module has been deprecated. Extend Node instead.` logs once per material build on r187 (`MToonAnimatedUVNode extends TempNode`). It's the only console noise (7 per Spec, 8 per VRoid). Changing `TempNode` to `Node` in the same file would remove it; it's left out of the patch to keep the patch minimal.
- `vite build` warns `IMPORT_IS_UNDEFINED: tslFn` for `FnCompat`'s pre-r168 branch. It never runs on r187 (`REVISION >= 168` takes `Fn`). Under webpack this namespace access is an error (#1890 thread); #1878 removes `FnCompat`.

## Gotchas this spike found

1. **Vite 8 can't contain the stock import at all.** Rolldown fails dependency pre-bundling (dev) and `vite build` on the missing export. `vite.config.js` excludes it from pre-bundling so the browser shows the native link error. The app build aliases it to a stub (`STOCK_STUB=1`).
2. **TSL arithmetic is variadic.** `v.mul(1, -1)` is `v·1·(−1)`. Per-component factors need `vec2(...)`/`vec3(...)` operands. Watch for this in any TSL the engine writes (the post stack, AB-T-0554).
3. **`modelViewPosition` isn't a fragment position.** In TSL it's the object's origin in view space. Fragment work wants `positionView`, or `positionViewDirection` (surface→camera, normalised).
4. **Read a WebGPU canvas in the same task as the render.** The page calls `toDataURL()` right after the last `render()`. The harness reads `window.__png`, not the canvas later.
5. **Mira and Hana are one model.** Both bundles carry Spec's `avatar.vrm` (identical renders), so the VRoid sample is there for clothing, normal maps and different MToon inputs. Its pictures stay local (it can't be shipped); its numbers are in the JSON.
6. **WebGPURenderer composites in linear light; WebGL composites in sRGB.** Every translucent material looks different between the two, MToon or not (`model=threealpha`). Compare opaque and translucent separately (`hide=transparent`).
7. **Stock VRoid masks are greyscale**, so an R-vs-B channel bug is invisible on real content. Controlled textures (a B-only mask, a quadrant matcap) catch what real models can't.
8. **To isolate a material difference, use spheres.** On characters, 66% of pixels differed and nothing pointed at a cause. Per-feature isolation (`features=matcap|rim|…`), then a flat-colour sphere per feature, then a quadrant matcap found each bug in one run.

## Run it

```bash
cd web && npm install            # postinstall writes src/vendor/three-vrm-nodes{,-loadonly}.js from the installed 3.5.5
node scripts/patch-three-vrm.mjs --check      # does the stock file still match the patch?
npm run repro -- --save          # Node load test → ../results/repro-node.json
node scripts/shots.mjs           # headless Chromium matrix (own Vite servers on 5251 and, for r186, 5252) → ../results/chromium{,.json}
node scripts/compare.mjs         # SSIM / pixel stats → ../results/compare.json, montages (A | B | Δ×4) → ../results/compare/
npm run dev                      # interactive: http://127.0.0.1:5251/?renderer=webgpu&model=mira&view=face&features=all
```

VRoid Hub sample (needs `/Volumes/DEV_ARCHIVE/vroid-vrm-dataset` mounted, or `VROID_DATASET=<dir>/vroid`):

```bash
cd web && python3 -I scripts/scan-vroid-dataset.py /Volumes/DEV_ARCHIVE/vroid-vrm-dataset/vroid > ../results/vroid-sample.json
node scripts/copy-models.mjs     # copies the 29 sample models to public/models/vroid-sample/ (git-ignored)
node scripts/shots.mjs --vroid-sample           # → ../results/chromium-vroid.json
SPIKE_OUT=wkwebview-vroid SPIKE_ORIGINS=scheme ../mac/scripts/run.sh --vroid-sample   # → ../results/wkwebview-vroid.json
```

```bash
mac/scripts/build.sh             # vite build (STOCK_STUB=1) + swiftc → mac/build/WebGPUMToonSpike.app (ad hoc signed, sandboxed)
mac/scripts/run.sh               # all cases, scheme and loopback → ../results/wkwebview{,.json}
SPIKE_ORIGINS=loopback SPIKE_CASES='renderer=webgpu&model=mira&timing=1&w=1920&h=1080' mac/build/WebGPUMToonSpike.app/Contents/MacOS/WebGPUMToonSpike
```
